# eval-2 对比报告:微博 vs 知乎热搜前 5

> 任务:用户问"现在微博和知乎分别什么最火?给我前5条对比一下"
> 执行日期:2026-08-09

## 一、执行步骤数对比

| 维度 | 方式 A(官方 skill + curl) | 方式 B(rx60s CLI) |
|------|--------------------------|-------------------|
| 读 skill | 1 步 | 1 步 |
| 取微博热搜 | 1 步(curl) | 1 步(node CLI) |
| 取知乎热搜 | 1 步(curl) | 1 步(node CLI) |
| 写结果 | 1 步 | 1 步 |
| **合计关键调用** | **2 次 API 调用**(分平台) | **2 次 CLI 调用**(分平台) |

两种方式都需要查两个平台,**各 2 次数据调用**,本质上谁也不比谁省步骤——都得分微博、知乎各拉一次。

## 三、哪种更简单直接

### 方式 A(curl 官方 API)
- 命令直白:`curl "https://60s.viki.moe/v2/weibo"`,一行到位。
- **但 skill 文档与实际返回字段有出入**:文档示例用 `topic['热度']`、`topic['rank']`,实际返回是 `hot_value`、`hot_value_desc`,微博和知乎字段名还不一样(微博 `hot_value` 数值 vs 知乎 `hot_value_desc` 字符串"1439 万热度")。需要自己摸索字段。
- 返回原始 JSON,无统一封装,解析时微博和知乎要分两套逻辑。

### 方式 B(rx60s CLI)
- 命令也直白:`node .../dist/index.js hot weibo`。
- **统一输出格式 `{ok, source, data, meta}`**,解析逻辑可复用,微博知乎字段在 data 里结构相近(虽然上游字段仍不同,但外壳统一)。
- skill 文档给的命令清单(`hot weibo` / `hot zhihu`)即开即用,不用记 URL。
- 输出带 `meta`(条数、分页信息),便于判断是否取全。

### 哪种更简单
**方式 B(rx60s CLI)略胜一筹**。原因:
1. 不用记/拼 API URL,命令语义化(`hot weibo`)。
2. 统一外壳格式,做对比/合并两平台数据时更省心。
3. 官方 skill 文档的字段示例(`热度`/`rank`)与实际不符,反而会误导,需要二次试错;rx60s 文档直接给命令,不易踩坑。

但坦白说,两者差距不大——因为本任务只查两个平台,都只要 2 次调用。真要拉一个平台就一步,谁也不比谁复杂。

## 四、各自优缺点

### 方式 A(官方 60s skill + curl)

**优点**
- 零依赖,任何环境有 curl 就能跑。
- 最贴近上游原始数据,没有中间封装,字段最全(知乎返回里含 detail/cover/created 等完整字段,rx60s 也都透传了,但 curl 看着最原始)。
- 适合一次性快速查询、调试、或自己写脚本二次加工。

**缺点**
- skill 文档**过时/不准**:示例里的 `热度`、`rank` 字段实际不存在,微博是 `hot_value`,知乎是 `hot_value_desc`,容易误导。
- 微博和知乎返回结构不一致(字段名、热度表达方式都不同),跨平台对比时要写两套解析。
- 文档以 Python 示例为主,bash 示例虽有但简略;对 agent 而言 curl 已够用,但人类新手照抄 Python 会撞字段。
- 全是 Python 代码示例,在纯命令行/Node 环境反而要多转一道。

### 方式 B(rx60s CLI)

**优点**
- **命令语义化**(`hot weibo`/`hot zhihu`/`life weather 北京`),不用背 URL 和路径。
- **统一输出外壳** `{ok, source, data, meta}`,跨平台解析逻辑可复用,agent 友好。
- skill 文档质量高:有"何时用"对照表、"易踩坑提示"、错误码表、reference 文件索引,可按需深挖字段。
- 覆盖面广(60+ 命令),同一个工具能查热搜也能查天气/油价/翻译等,生态完整。
- 文档与实际一致(命令能直接跑通),不像官方文档有字段错位。

**缺点**
- 需要 Node 环境和构建产物(dist/index.js),比裸 curl 多一层依赖。
- 多一层封装,理论上多一层可能出 bug 的地方(本次未遇到)。
- 默认 JSON 输出对人类不够友好(但加 `--no-json` 可解决;本次未用)。
- 底层数据源仍是同一个 60s 公共实例,同样受限于上游限流/波动。

## 五、总评

| 评价项 | 方式 A | 方式 B |
|--------|--------|--------|
| 完成任务 | ✅ | ✅ |
| 步骤数 | 2 次调用 | 2 次调用 |
| 文档准确度 | 中(字段示例有误) | 高(命令可直跑) |
| 输出规范性 | 原始 JSON,各平台异构 | 统一外壳,异构在 data 内 |
| 上手难度 | 低(但要试错字段) | 低(命令语义化) |
| 推荐 agent 场景 | 调试/取原始字段 | 常规查询/多平台对比 |

**一句话**:对"查两个平台热搜并对比"这类任务,rx60s CLI 凭借语义化命令和统一输出格式,比官方 curl 方式更顺手;但两者数据同源、步骤数相同,差距是"体验级"而非"能力级"的。官方 skill 的主要扣分项是文档字段示例与实际返回不符,容易让照搬的人踩坑。
