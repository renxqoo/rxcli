# 多步任务对比评测:官方 60s skill vs rx60s CLI

> 任务:用户问"今天有什么新闻?顺便帮我查下北京天气"
> 场景类型:**多步组合任务**(查新闻 + 查天气,2 个独立子任务)
> 评测日期:2026-08-09

---

## 一、执行步骤对比

### 方式 A:官方 60s skill(直接 curl API)

| 步骤 | 动作 | 说明 |
|------|------|------|
| 1 | 读 skill 文件 `daily-news-60s.md` | 学新闻 API 用法 |
| 2 | 读 skill 文件 `weather-query.md` | 学天气 API 用法 |
| 3 | `curl https://60s.viki.moe/v2/60s` | 取新闻(第 1 次网络请求) |
| 4 | `curl https://60s.viki.moe/v2/weather/realtime?query=北京` | 取天气(第 2 次网络请求) |

- **读文件数:2 个 skill 文件**(每个子任务一个,各自独立)
- **网络调用数:2 次 curl**(新闻 1 次 + 天气 1 次)
- **踩坑**:天气请求的中文 `query=北京` 直接传会返回 HTTP 400,必须手动 URL 编码成 `query=%E5%8C%97%E4%BA%AC`。skill 文档里的 bash 示例 `curl "...?query=北京"` 照抄会失败,需要 agent 自行判断处理。

### 方式 B:rx60s CLI

| 步骤 | 动作 | 说明 |
|------|------|------|
| 1 | 读 skill 文件 `SKILL.md`(1 个) | 学整体用法,新闻和天气命令都在里面 |
| 2 | `node dist/index.js 60s` | 取新闻(第 1 次网络请求) |
| 3 | `node dist/index.js life weather 北京` | 取天气(第 2 次网络请求) |

- **读文件数:1 个 skill 文件**(单一 SKILL.md 覆盖所有子任务)
- **网络调用数:2 次 CLI 调用**(新闻 1 次 + 天气 1 次)
- **踩坑**:无。中文城市名直接作为位置参数传入即可,CLI 内部处理编码。

---

## 二、数据一致性对比

### 新闻数据
- **15 条新闻标题**:完全一致(逐字相同)
- **日期 / 星期 / 农历**:一致(2026-08-09 星期日 丙午年六月廿七)
- **每日微语**:完全一致
- **覆盖图 / 图片链接 / 文章链接**:一致

### 天气数据
| 字段 | 方式 A (curl) | 方式 B (CLI) | 是否一致 |
|------|---------------|--------------|----------|
| 天气状况 | 晴 | 晴 | ✅ |
| 温度 | 27°C | 27°C | ✅ |
| 湿度 | 54% | 53% | ⚠️ 差 1% |
| 气压 | 1006 hPa | 1006 hPa | ✅ |
| 风向 | 南风 | 东南风 | ⚠️ 略有差异 |
| 风力 | 3-4 级 | 3-4 级 | ✅ |
| AQI | 47 | 47 | ✅ |
| 空气质量等级 | 优 | 优 | ✅ |
| 日出/日落 | 05:21 / 19:19 | 05:21 / 19:19 | ✅ |
| 生活指数 | 完全一致 | 完全一致 | ✅ |

**结论**:新闻数据完全一致。天气数据有极微小差异(湿度差 1%、风向从"南风"变"东南风"),原因是两次调用相隔约 5 分钟,天气源在这期间更新了一次(方式 A 的 `updated` 是 23:00,方式 B 是 23:05)。**这种差异是数据源时间差造成的,不是工具本身的问题**——两个工具背后是同一个 60s API。

> 附带发现一个小数据差异:同一条 UFO 新闻,方式 A 拿到的文本是"光球飞掠**东**居民区",方式 B 是"光球飞掠**中东**居民区"。这是上游 API 在两次调用间自身做了文本修订,与工具无关。

## 三、多步组合场景适配性分析

### 维度 1:认知负担 / 上下文占用

| 维度 | 方式 A(官方 skill) | 方式 B(rx60s CLI) |
|------|---------------------|----------------------|
| 多步任务需读几个 skill 文件 | **N 个**(每类需求一个文件) | **1 个**(单一 SKILL.md) |
| 本任务实际读取 | 2 个(daily-news + weather-query) | 1 个 |
| 若任务扩展到 3 步(如再加油价) | 需读第 3 个 skill 文件 | 仍只需读 1 个,SKILL.md 里查命令 |

**多步任务下方式 B 优势明显**:子任务越多,方式 A 需要加载的 skill 文件线性增长,上下文占用和切换成本也线性增长;方式 B 始终是 1 个文件。

### 维度 2:调用一致性 / 出错率

| 维度 | 方式 A | 方式 B |
|------|--------|--------|
| 不同子任务的调用方式 | 各异(新闻走 `/v2/60s`,天气走 `/v2/weather/realtime`,路径/参数风格不统一) | 统一(`rx60s <域> <命令> [位置参数] [flags]`) |
| 中文参数处理 | 需手动 URL 编码,照抄文档示例会 400 报错 | CLI 自动处理,直接传中文即可 |
| 返回格式 | 上游裸 JSON(字段结构因接口而异) | 统一 `{ok, source, data, meta}` 信封,所有命令一致 |

**多步任务下方式 B 更稳**:agent 不用为每个子任务重新学一套调用约定,学一次范式复用 N 次。

### 维度 3:网络调用次数

- 两种方式**完全相同**:都是 2 次(每个子任务 1 次真实 API 请求)。
- 方式 B 没有因为包了一层 CLI 就多打网络请求,底层一一对应。

### 维度 4:可组合性 / 管道串联

- 方式 A 的 curl 输出是上游原始 JSON,格式不统一,要串联管道(如 `查天气 → 按温度给建议`)需自己写适配逻辑。
- 方式 B 输出统一 JSON 信封,且 SKILL.md 明确说明"管道下游时强制 JSON,保护下游解析",天然适合 `CLI | jq | 下一步` 的组合。

---

## 四、总结

| 对比项 | 方式 A(官方 skill) | 方式 B(rx60s CLI) | 胜出 |
|--------|---------------------|----------------------|------|
| 读 skill 文件数 | 2 | 1 | **B** |
| 网络调用数 | 2 | 2 | 平 |
| 数据准确性 | 准确 | 准确 | 平 |
| 调用一致性 | 每个接口一套约定 | 统一范式 | **B** |
| 中文参数易用性 | 需手动 URL 编码,文档示例有坑 | 直接传,无坑 | **B** |
| 返回格式统一性 | 上游裸 JSON,格式各异 | 统一 `{ok,source,data}` 信封 | **B** |
| 扩展到更多子任务 | 文件数和上下文线性增长 | 始终 1 个文件 | **B** |
| 管道可组合性 | 需自己适配 | 天然支持 | **B** |

### 结论

**对于多步组合场景,rx60s CLI(方式 B)明显更合适**:

1. **认知开销低且恒定**:无论任务是 1 步还是 5 步,只需读 1 个 SKILL.md;方式 A 的 skill 文件数随子任务种类线性增长。
2. **调用范式统一**:所有子任务用同一套 `rx60s <域> <命令>` 语法,学一次复用多次;方式 A 每个接口的路径、参数名、返回结构都不一样。
3. **避坑**:方式 A 的天气接口中文参数需手动 URL 编码(文档示例照抄会 400),方式 B 无此问题。
4. **数据等价**:两者背后是同一个 60s API,数据完全等价(微小时间差造成的字段波动与工具无关)。

方式 A 的优势在于**零依赖**(只要有 curl/requests 就能跑,不需要 Node 环境),适合极简环境或单次一次性查询。但一旦任务变成多步组合,方式 B 的统一性和低认知负担优势就非常突出。
