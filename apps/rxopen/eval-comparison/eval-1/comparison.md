# 天气查询评测对比报告

**任务**：用户问"杭州今天天气怎么样？温度多少，空气好不好"
**评测日期**：2026-08-09
**查询时间**：约 23:05（数据更新时间戳一致）

---

## 一、执行步骤对比

| 维度 | 方式 A：官方 skill + curl | 方式 B：rx60s CLI |
| --- | --- | --- |
| 前置阅读 | 读 1 份 skill（`weather-query.md`，268 行） | 读 1 份 skill（`SKILL.md`，206 行） |
| 实际调用 | 1 步：`curl "https://60s.viki.moe/v2/weather/realtime?query=杭州"` | 1 步：`node dist/index.js life weather 杭州` |
| 遇到困难 | 无 | 无 |
| 总步数 | **1 步** | **1 步** |

两种方式都是**单次调用**就拿到了用户需要的全部信息（温度、天气状况、空气质量一次返回），无需二次请求。

## 三、易用性 / 简洁度

### 哪种更简单直接？

对于**当前这个单点天气查询**任务，两者几乎一样简单——都是一条命令。但细节上有差别：

- **方式 A（curl）**：需要记住 API URL 路径（`/v2/weather/realtime`）、参数名（`query`），并对城市名做 URL 编码（杭州 → `%E6%9D%AD%E5%B7%9E`）。skill 文档里这些信息齐备，但"记住端点路径"对 agent 是额外认知负担。
- **方式 B（rx60s）**：命令是自然语义的 `life weather 杭州`，城市直接作为位置参数，无需关心 URL、无需编码。SKILL.md 里明确提示"城市是位置参数不是 `--query`"，避免踩坑。

结论：**从"写出正确命令"的角度，rx60s CLI 稍微更直接**（不用记 URL/参数名/编码），尤其对不熟悉 API 细节的场景。

## 四、各自优缺点

### 方式 A：官方 60s skill + curl

**优点**
- 零依赖，任何能联网的环境都能用（curl 几乎处处可用）。
- 最贴近数据源，没有中间封装层，调试/排查问题时响应链路最短。
- 通用性强：同一个 API base 下还能调 `forecast`、热搜、油价等几十个端点。

**缺点**
- 需要记端点路径和参数名；中文城市名要 URL 编码。
- 返回是裸 JSON（`{code,message,data}`），没有 agent 友好的统一封装，下游解析要自己取 `data`。
- 不同接口的返回结构各不相同，agent 解析每类数据都要单独适应。
- 没有内置错误归一化、限流重试、自部署切换等机制。

### 方式 B：rx60s CLI

**优点**
- 命令语义化、好记（`life weather <城市>`），参数符合直觉，城市名直接传。
- 输出统一格式 `{ok, source, data, meta}`，agent 解析逻辑可复用，`ok` 字段便于判断成败。
- 错误处理已归一化（`not_found` / `invalid_argument` / 429 限流 / 5xx 等），并支持 `RX60S_BASE_URL` 切换自部署实例规避限流。
- 一个 CLI 覆盖 60+ 类接口，技能内聚（news / hot / life / tool 等），不用为每类数据记不同 URL。
- `--no-json` 还能输出人类可读的卡片/表格，agent 与终端场景两用。

**缺点**
- 需要 Node 运行时和构建产物（`dist/index.js`），比 curl 重。
- 多一层封装，理论上多一层出错可能（不过本次未出现）。
- 绑定单一框架（`@renxqoo/agent-data-cli`），对不用该框架的环境接入成本略高。

---

## 五、总结

|  | 方式 A（官方 curl） | 方式 B（rx60s CLI） |
| --- | --- | --- |
| 步数 | 1 | 1 |
| 数据 | 实时、完整 | 实时、完整（与 A 完全一致） |
| 易用 | 中（需记 URL/编码） | 高（语义化命令） |
| 依赖 | 无（仅 curl） | Node + dist 产物 |
| 适合场景 | 临时查询、调试、轻量环境 | agent 工作流、批量接口、生产可观测 |

**实事求是结论**：在这个具体任务上，两种方式**产出完全等价**，都是 1 步搞定，数据一致。差异主要在工程化层面——rx60s CLI 用语义化命令和统一输出封装降低了 agent 的认知与解析成本，更适合作为 agent 的常驻工具；官方 curl 则胜在零依赖、最轻量，适合一次性查询或排障。两者**互补**而非对立。
