# rx60s CLI vs 官方 60s skill 真实评测报告

> 5 个真实需求场景,每个场景两个子 agent 并行跑(官方 skill 直接 curl vs rx60s CLI),全部真实调用 60s API。
>
> 评测日期:2026-08-09 | 数据源同一(60s API)

---

## 一、总览

| # | 场景 | 类型 | 官方 skill | rx60s CLI | 胜出 |
|---|------|------|-----------|-----------|------|
| 1 | 查杭州天气 | 简单单接口 | ✅ 1步完成 | ✅ 1步完成 | 平(能力等价) |
| 2 | 微博+知乎热搜对比 | 多平台列表 | ⚠️ 文档字段示例与实际不符 | ✅ 一次跑通 | **rx60s** |
| 3 | 翻译(带参数) | 非显然参数 | ❌ 接口未覆盖,4步含2次失败探测 | ✅ 2步0失败 | **rx60s** |
| 4 | 新闻+天气(多步) | 多步组合 | ⚠️ 读2个skill+中文编码坑 | ✅ 读1个skill+无坑 | **rx60s** |
| 5 | 密码生成(参数陷阱) | 易踩坑 | ❌ 接口未覆盖+静默答错 | ✅ 易踩坑提示精准避开 | **rx60s** |

**5 局结果:rx60s 胜 4 局,平 1 局,负 0 局。**

---

## 二、关键发现(按重要性排序)

### 🔴 发现 1:官方 skill 接口覆盖不全(翻译、密码完全没文档)

评测3(翻译)和评测5(密码)暴露了官方 skill 的结构性短板:

- **翻译接口**:6 个 skill、1463 行文档,搜 `translate/fanyi/翻译` **零命中**。agent 只能猜端点 `/v2/translate`(404)→ 改猜 `/v2/fanyi`(400 报错反推参数名)→ 最终 4 步含 2 次失败才跑通。
- **密码接口**:同样零文档。更严重的是 agent 不知道 `symbols` 默认关,生成的密码**不含特殊符号**却仍被 API 评为"极强"——**静默答错,agent 自己都察觉不到**。

rx60s CLI 的命令表 + 易踩坑提示直接覆盖了这些场景,2 步 0 失败完成。

### 🟡 发现 2:官方 skill 文档与实际返回不符

评测2(热搜)发现:官方文档示例用 `topic['热度']`、`topic['rank']`,实际返回是 `hot_value`(微博)和 `hot_value_desc`(知乎),字段名还不一样。**照搬文档示例会踩坑,需二次试错。**

### 🟡 发现 3:官方 skill 中文参数需手动 URL 编码

评测4(多步)发现:天气接口 `query=北京` 直接传返回 HTTP 400,必须手动编码成 `query=%E5%8C%97%E4%BA%AC`。**文档里的 bash 示例 `curl "...?query=北京"` 照抄会失败。** rx60s CLI 的位置参数自动处理编码,无此问题。

### 🟢 发现 4:简单场景两者等价

评测1(单接口查天气):两种方式都是 1 步完成,数据 100% 一致。简单查询场景下,官方 curl 的零依赖优势与 rx60s 的语义化命令优势抵消,能力等价。

## 三、维度对比

| 维度 | 官方 skill(curl) | rx60s CLI |
|------|-------------------|-----------|
| **接口覆盖** | 6 个 skill 覆盖约 28 个端点(缺翻译/密码/OG/WHOIS 等) | 68 个接口全覆盖 |
| **参数可知性** | 需猜端点+参数名+枚举值(语言代码等) | 命令表+易踩坑提示+references 全标明 |
| **默认值陷阱** | 无提醒(symbols 默认关等陷阱会静默答错) | 易踩坑提示精准覆盖 |
| **文档准确性** | 字段示例与实际返回不符 | 命令签名从代码生成,不漂移 |
| **中文参数** | 需手动 URL 编码 | 自动处理 |
| **多步任务** | 读 N 个 skill 文件,上下文线性增长 | 读 1 个 SKILL.md,恒定 |
| **输出格式** | 上游裸 JSON(各接口字段不同) | 统一 `{ok,source,data,meta}` |
| **错误处理** | HTTP status + message | 9 类类型化错误 + exit code + 友好提示 |
| **依赖** | 零(curl 系统自带) | 需 Node + npm 包 |
| **启动开销** | 直连 API,无中间层 | Node 进程启动(毫秒级) |

## 四、结论(实事求是)

### 我之前的判断是错的

我之前说"rx60s-cli 没有必要,curl 更优"——**这个判断是错的。** 它基于一个错误假设:"官方 skill 已经全面准确地教 agent 怎么用 60s API"。实测发现官方 skill **接口覆盖不全、文档有错、参数不自描述、无陷阱提醒**,agent 在翻译和密码场景直接答错或大幅试错。

### rx60s CLI 的真实价值(评测证实)

1. **全覆盖**:68 个接口 vs 官方 ~28 个,翻译/密码/WHOIS 等官方漏的都覆盖
2. **参数可知**:命令签名 + 易踩坑提示,agent 不用猜端点/参数名/枚举值
3. **避坑**:symbols 默认关、语言代码、中文编码这些陷阱,rx60s 有提醒,官方没有
4. **文档准确**:命令签名从代码生成(gen.ts),不像官方手写文档会与实际脱节
5. **多步友好**:1 个 SKILL.md 覆盖所有,不随子任务数增长

### 官方 skill 仍有优势的场景

- **零依赖**:只要有 curl 就能跑,不需要 Node 环境
- **极简查询**:查个新闻/天气,官方够用且更轻
- **Python 环境**:官方 skill 给了 Python 示例,适合 Python agent

### 最终建议

**rx60s CLI 有必要保留。** 它的价值不是"封了一层 API",而是:
- 补全了官方 skill 漏掉的接口覆盖
- 用代码生成的命令签名保证了文档准确性
- 用易踩坑提示帮 agent 避开默认值陷阱
- 统一输出格式便于 agent 解析和管道组合

对于"让 agent 可靠地用好 60s 全部 68 个接口"这个目标,rx60s CLI 显著优于官方 skill。官方 skill 更适合轻量/零依赖的单次查询。
