# eval-5 对比报告:生成 20 位含特殊符号的强密码

> 任务原文:"生成一个 20 位的强随机密码,要包含特殊符号,顺便告诉我它有多安全"
>
> 隐藏陷阱:`password` 接口的 `--symbols`/`symbols` **默认关闭**。用户要"包含特殊符号",必须显式开启;否则只会生成"字母+数字"。

---

## 一句话结论

**在"参数默认值陷阱"这类场景下,rx60s 明显更可靠。** 官方 skill 既没文档化密码接口、也没提醒 symbols 默认关,只读官方 skill 的 agent 会**静默答错**;rx60s 靠 SKILL.md 里一段"易踩坑提示"精确预警了陷阱,生成的密码真正含符号。

---

## 一、官方 skill 有没有覆盖密码接口?有没有提醒 symbols 默认关?

**都没有。**

- `all_official_skills.md` 共 6 个 skill:daily-news-60s、hot-topics、weather-query、data-query、entertainment、media-info。
- 全文搜索 `password` / `密码`:**各 0 次命中**。
- 也就是说官方 skill 里**压根没有"密码生成"这个接口的文档**,更谈不上提醒"`symbols` 默认关"这个陷阱。

直接后果:只依赖官方 skill 的 agent 根本不知道有 `/v2/password` 这个端点,只能靠"猜"(endpoint 名 `password` 比较显眼,猜中概率尚可),但**绝不会知道有个叫 symbols 的开关、且它默认是关的**。

## 二、rx60s 的"易踩坑提示"是否帮你避开了陷阱?

**是的,精准避开。**

rx60s 的 SKILL.md 有一段专门的 **"易踩坑提示(参数默认值/非显然值)"**,第一条就是:

> **`tool password` 的 `--symbols` 默认关**:用户要"含特殊符号的密码"必须显式加 `--symbols`,否则只生成字母+数字。其它(`--numbers`/`--lowercase`/`--uppercase`)默认开。

这段话和用户的诉求("要包含特殊符号")**一一对应**,我据此直接构造了 `rx60s tool password --length 20 --symbols`,没踩坑。

补充验证:只看 `--help` 是**看不出陷阱**的——`--symbols` 和 `--numbers`/`--lowercase`/`--uppercase` 在 help 里长得一模一样,都是 `[--xxx]`,没有任何线索表明"只有 symbols 默认关"。这正是"易踩坑提示"存在的价值:它补的是 `--help` 看不出的非对称默认值。

## 三、两种方式生成的密码是否都包含特殊符号?

**只有方式 B(rx60s)的密码含特殊符号;方式 A(官方 skill)不含。**

| 维度 | 方式 A:官方 skill | 方式 B:rx60s CLI |
|------|------------------|-----------------|
| 怎么知道命令/endpoint | 没文档,只能猜 `/v2/password` | SKILL.md 命令表 + 易踩坑提示 |
| 实际调用 | `curl ".../v2/password?length=20"` | `rx60s tool password --length 20 --symbols` |
| 是否传了 symbols | ❌ 没有(不知道有这参数) | ✅ 有(SKILL.md 提醒了) |
| 生成密码 | `vr3qAeUfAPzWt8QnbAqb` | `A!8#%T_X3tw@@n^F2!6A` |
| `include_symbols` | `false` | `true` |
| 符号字符集 | `""`(空) | `!@#$%^&*_+-=|:?` |
| **是否含特殊符号** | ❌ **不含**(踩坑) | ✅ **含** `! # % _ @ ^` |
| 用户核心诉求满足度 | ❌ 不满足 | ✅ 满足 |
| 熵(生成熵) | 115.63 bit(字母+数字) | 122.59 bit(四类齐全) |
| password-check 复检 | 未做(无此意识) | 100 分 / 极强 / 131.09 bit |
| API 自评强度 | 极强 | 极强 |

注意一个**更隐蔽的问题**:方式 A 的密码虽然不含符号,API 仍给它评了"极强 / 数百万年"。也就是说**连上游接口本身都不会主动提示"你忘开 symbols 了"**——`include_symbols:false` 这个信号就静静躺在 JSON 里,没有文档提示 agent 去看它。这放大了"静默答错"的危害:agent 会带着"已达标"的错觉把一个不符合诉求的密码交给用户。

## 四、这个"参数陷阱"场景下哪种更可靠

**rx60s 更可靠,而且是数量级上的差距。**

| 评估项 | 官方 skill | rx60s |
|--------|-----------|-------|
| 接口是否文档化 | ❌ 没有密码接口 | ✅ 命令表里有 |
| 是否提醒"symbols 默认关" | ❌ 无任何提示 | ✅ 易踩坑提示专门点出 |
| 能否避开陷阱 | ❌ 几乎必然踩坑 | ✅ 稳稳避开 |
| 答错后能否自我察觉 | ❌ 无法察觉(无文档对照) | ✅ 能对照 config 字段确认 |
| 生成的密码满足用户诉求 | ❌ 不含符号 | ✅ 含符号 |

**根因分析:**

- 官方 skill 的失败是**双重失败**:(1) 接口缺失 → agent 只能猜;(2) 即便猜中 endpoint,也因为没有"默认值非对称"的提醒而漏开 symbols。两层都没有护栏。
- rx60s 的成功是**两层护栏**:(1) 命令表明确列出 `tool password` 的所有参数;(2) "易踩坑提示"用自然语言把"`--symbols` 默认关、其它默认开"这个**光看参数列表看不出来的非对称性**直接讲明白。第二层是关键——它针对的就是"参数长得一样、行为却不一样"这类陷阱。

**适用范围结论:** 对"参数默认值陷阱 / 非显然默认行为"这类任务(本例:要符号但 symbols 默认关;类似地还有"要中文翻译但目标语代码要查表"、"要城市天气但城市是位置参数不是 flag"等),**rx60s 的"易踩坑提示"机制能显著降低 agent 静默答错的概率,明显比只有接口文档(甚至文档缺失)的官方 skill 更可靠。** 这个优势在"看起来都成功、实际一个错一个对"的隐蔽场景里尤其有价值。
